# ADR-0021: Public Resource Identifier Architecture (Public UUIDv7 Defense-in-Depth & Anti-Enumeration)

## Status
**Accepted**

## Context & Problem Statement
Domain entities in MyBooking (e.g., `app_user`, `reservation`, `room`, `event_booking`, `feedback`) currently use sequential, auto-incrementing integer / bigint primary keys (`BIGINT GENERATED BY DEFAULT AS IDENTITY`).

While Spring Security and domain services enforce strict object-level authorization (BOLA/IDOR protection), exposing sequential integers directly across public REST endpoints (e.g., `/api/client/reservations/42` or `/api/feedback/15`) introduces security and operational risks:
1. **Resource Enumeration & Scraping**: Attackers can trivially increment or decrement identifiers to discover resource ranges, probe for gaps, or test access-control edge cases.
2. **Business Intelligence Leakage**: Sequential IDs reveal business volume, transaction frequency, guest acquisition velocity, and hotel reservation metrics to external parties.
3. **Defense-in-Depth Gap**: Relying exclusively on authorization logic without identifier obfuscation leaves no safety buffer in the event of an authorization policy regression.

We must define an architecture for public-facing identifiers that provides non-enumerable, collision-resistant identifiers without compromising database indexing performance or relational integrity.

## Decision Drivers
* **Defense-in-Depth & Anti-Enumeration**: Public identifiers must be high-entropy, globally unique, and non-enumerable (`SEC-API-001`, `SEC-DATA-001`).
* **Database Indexing Performance**: Avoid random UUIDv4 write penalties, B-tree index fragmentation, and buffer-pool thrashing in PostgreSQL.
* **Separation of Concerns (Internal vs. External)**: Internal database joins, foreign keys, and storage optimizations must remain decoupled from external API representation.
* **Standards Alignment**: Adhere to RFC 9562 (UUID Version 7: time-ordered 128-bit identifiers).
* **Controlled Phasing**: Schedule adoption for **MILESTONE IdP (Keycloak IdP, Next.js BFF & Public UUIDv7 Architecture)** immediately following Phase 03 domain refactoring and prior to Phase 04 schema isolation, ensuring Phase 02 and Phase 03 complete without disruptive schema churn.

## Considered Options
1. **Option 1: Expose Sequential Integer Primary Keys (`BIGINT id`) Directly**:
   - *Pros*: Zero migration effort; optimal join and indexing efficiency.
   - *Cons*: Trivially enumerable; leaks transaction volumes; violates defense-in-depth standards.
2. **Option 2: Replace All Primary Keys with Random UUIDv4**:
   - *Pros*: Uniform schema; entities have a single identifier everywhere.
   - *Cons*: Severe PostgreSQL B-tree page splitting on high-concurrency inserts; degrades cache hit ratios; expands foreign key storage by 2x to 4x.
3. **Option 3: Dual-Key Pattern with Public UUIDv7 (`public_id`) (Chosen)**:
   - Entities maintain an internal `BIGINT id` as the primary key and for all relational foreign-key joins.
   - Entities maintain a secondary indexed, immutable column: `public_id UUID NOT NULL UNIQUE`.
   - `public_id` values are generated using time-ordered UUIDv7 (RFC 9562).
   - All external DTOs, REST URLs, and client API contracts expose `public_id` exclusively. Internal SQL joins continue to use the high-performance `BIGINT id`.

## Decision Outcome
**Chosen Option**: **Option 3: Dual-Key Pattern with Public UUIDv7 (`public_id`)**.

### 1. Dual-Key Architecture
```
   [ External REST API Client / Next.js BFF ]
                   │
                   ▼  GET /api/reservations/018e3a2f-7c1a-7b3e-8f2e-4b6c8d9e0f1a
   [ Spring Boot Controller / DTO Tier ]
                   │
                   ▼  reservationRepository.findByPublicId(publicId)
   [ PostgreSQL Relational Layer ]
   ┌────────────────────────────────────────────────────────────────────────┐
   │ Table: reservation                                                     │
   │  id: BIGINT (PK, clustered index, internal FK target)                 │
   │  public_id: UUID (UNIQUE, B-tree index, time-ordered UUIDv7)           │
   │  client_id: BIGINT (FK -> app_user.id)                                 │
   │  room_id: BIGINT (FK -> room.id)                                       │
   └────────────────────────────────────────────────────────────────────────┘
```

### 2. Identifier Generation Standard (UUIDv7)
- Public identifiers **MUST** adhere to RFC 9562 UUIDv7.
- UUIDv7 embeds a 48-bit millisecond Unix timestamp in the most significant bits followed by cryptographically secure random bits:
  - Preserves chronological sortability in database indexes.
  - Eliminates the random I/O and index page-splitting associated with random UUIDv4.
  - Compatible with standard 128-bit PostgreSQL `UUID` column types.

### 3. Execution Roadmap & Phase Allocation
- **Phase 02 (Current)**: Baseline security controls, Spring Security Resource Server adoption, and `@AuthenticationPrincipal` identity injection. No schema migration.
- **Phase 03 (Target Implementation)**:
  1. Add Flyway database migrations introducing `public_id UUID NOT NULL DEFAULT gen_random_uuid()` (or Java-generated UUIDv7) to public entities (`app_user`, `reservation`, `room`, `event_booking`, `feedback`, `loyalty_account`).
  2. Create unique B-tree indexes: `CREATE UNIQUE INDEX idx_reservation_public_id ON reservation(public_id);`.
  3. Update REST DTOs and controllers to accept and emit `public_id` instead of numeric `id`.
  4. Next.js BFF updates routes to use `public_id` exclusively.

## Consequences & Operational Impact
* **Positive**:
  * Prevents all sequential identifier enumeration across the platform.
  * Hides real business activity, reservation counts, and user acquisition numbers from competitors and malicious scrapers.
  * Preserves high-performance integer foreign key joins and compact storage inside PostgreSQL.
* **Negative**:
  * Requires one additional indexed column (`public_id`) per public entity table.
  * Domain services perform lookups by `public_id` on incoming API requests rather than direct primary key lookups (mitigated by the unique B-tree index).
